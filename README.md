# Avito SERP Analyzer

Инструмент исследования ниши Avito для **решения о входе** (вторичный сценарий — обзор рынка для действующего продавца): анализ поисковой выдачи из Excel-файла — кластеры спроса, свежесть, конкуренты, незакрытые сценарии. Вход — Excel-выгрузка парсера поисковой выдачи по ключевому запросу + ниша и регион; выход — Markdown-отчёт-обзор факторов входа (секции 1–9) с явным вердиктом. Метрики и бакеты считает код, аналитику пишет LLM (OpenAI-совместимый API).

**SaaS с аккаунтами**: регистрация через Supabase (email + пароль, подтверждение по письму), история отчётов в аккаунте (Markdown + исходный Excel), квоты анализов с 30-дневным окном, экспорт DOCX.

## Как это работает

1. **Парсинг Excel** — fuzzy-маппинг ядерных колонок (`Заголовок`, `Цена`, `Дата публикации`, `Просмотров всего`, `Платные услуги`, продавец, `категория 1–6` и т.д.). Товарные колонки ниши (`Высота`, `Материал`…) игнорируются с предупреждением. Нет ядерной колонки — значения `[НЕТ ДАННЫХ]`, анализ не ломается.
2. **Метрики (код)** — две категории объявлений: **свежие** («Дата публикации» ≤7 дней + подтверждение связкой «Просмотров сегодня» ↔ «Просмотров всего») и **старые** (всё остальное, включая продлённые). Время парсинга фиксируется и попадает в отчёт: «Просмотров сегодня» — главный сигнал эффективности, привязанный к нему. «Просмотры/день» не считаются: «Дата публикации» в выгрузке Avito — дата продления, а «Всего просмотров» накапливается за всю жизнь объявления. **Ценовая сегментация**: цена — конфаундер просмотров, поэтому объявления с числовой ценой делятся на три сегмента — **дешёвые / средние / дорогие** (тертили: дешёвые ≤ p33 < средние ≤ p66 < дорогие; <9 с ценой — сегменты не считаются, «договорная» и цена без числа — вне сегментов), и все разрезы просмотров (свежие vs старые, promo-эффект) считаются **внутри сегментов**.
3. **Стадия A (LLM, JSON, temperature=0)** — каждому объявления: теги кластеров (товарный / характеристический / сценарный / проблемный / коммерческий), B2C/B2B, поисковые запросы, УТП, сценарий. Теги проходят **очистку кодом** (`src/metrics.py::normalize_cluster_tag`): мусорные запросы (пометки состояния/подачи — «дефекты», «бесплатно после стирки», «следы эксплуатации», «уценка»), дубли регистра и варианты размеров (→ один тег «размеры») исключаются/склеиваются. Retry 1× при невалидном JSON; при фолбэке карта спроса заполняется `[НЕТ ДАННЫХ]`.
4. **Дайджест (код)** — в него входят **ключевые факты, посчитанные кодом** (объём, классы свежести, нулевые просмотры, концентрация топ-10, promo-эффект, свежие vs старые, цена vs спрос, продавцы, кластеры без свежих, B2B-доля, топ-5 запросов, цены по кластерам, **реалистичные пороги** — потолок «Критерия успеха» по просмотрам = 2× медианы «Просмотров сегодня» сегмента; пустая база → `[НЕТ ДАННЫХ]`), **таблицы с ценовым контролем** — «Сегменты цены: дешёвые / средние / дорогие» (границы тертилей — сплошное разбиение без «дырок», N, цена min–med–max, медиана «Просмотров сегодня», доля платных услуг), «Свежие vs старые внутри ценовых сегментов», «Цены по кластерам» и «Эффективность свежих vs старых (без учёта цены)» с примечанием, что сравнение по всей выдаче конфаундится ценой, поля Стадии A в каждой записи (запросы, УТП, сценарий, тип), **правила интерпретации с сезонностью** (месяц парсинга, «0 свежих» у сезонного товара = закрытый сезон, а не окно входа; товар клиента — основа гипотез; сервис ≠ сценарий; юнит-экономика `[НЕТ ДАННЫХ]`) и **карта спроса (код)** — точные счётчики «кластеры × бакеты» (после очистки тегов) плюс ценовые столбцы (цена-медиана и счётчики сегментов по тегу; <9 с ценой → `[НЕТ ДАННЫХ]`), числа от LLM не зависят.
5. **Стадия B (LLM)** — финальный Markdown-отчёт секций 1–9, организованный факторами решения о входе: §8 — гипотезы (строго 5–10 в формате `**Гипотеза N: …** — Основание: …; Проверка: …; Критерий успеха: <измеримый порог с числом>`; порядок гипотез = приоритет, гипотеза 1 — главная ставка и она же пункт 6 §9; гипотезы обязаны быть релевантны товару клиента, основание «0 свежих» требует проверки сезона, основание на 1–2 объявлениях → маркер, сервисные гипотезы «с доставкой» запрещены, порог просмотров ≤ факта «реалистичные пороги» либо в «Проверке» бюджет на продвижение), §9 — «Решение о входе»: первая строка `**Вердикт:** ВХОДИТЬ ПРИ УСЛОВИИ … | НЕ ВХОДИТЬ` (либо маркер `[НЕДОСТАТОЧНО ДАННЫХ ДЛЯ РЕШЕНИЯ]`; **безусловный «ВХОДИТЬ» запрещён** — юнит-экономика не измерена, вердикт обязан называть целевой ценовой сегмент) — основание вердикта = ожидаемые просмотры на объявление в целевом ценовом сегменте (медиана «Просмотров сегодня») + ценовое позиционирование; сразу после вердикта две обязательные оговорки (проверяются валидацией): **«второй этап воронки»** (данные измеряют только просмотры, конверсия — гипотетика) и **юнит-экономика** (себестоимость/маржа/CAC — `[НЕТ ДАННЫХ]`, вердикт — о трафике, не о прибыли) + ровно 7 пунктов `1)`–`7)` (п.1 — ожидаемый результат: просмотры в сегменте, п.4 — продвижение как вложение продавцов в трафик → трафик окупается, п.7 — «что делаем → основание (цифра) → эффект/как измеряем (критерий успеха с числом)»); каждое утверждение §8–9 обязано опираться на цифру из дайджеста или содержать маркер `[НЕТ ДАННЫХ]` (в «Критерии успеха» маркер запрещён). Ответ проходит **валидацию Grounding** (`src/llm.py::validate_grounding`): подстроки «Основание»/«Проверка»/«Критерий успеха», числовой порог в критерии, цифра-цитата из дайджеста, запрет «Основания» на 1–2 объявлениях, запрет темы «дефекты/б/у» и сервиса (доставка/оплата) в гипотезах (кроме ниш-услуг), требование проверки сезона при основании «0 свежих», потолок KPI по просмотрам из факта «реалистичные пороги» (обход — бюджет на платные услуги в «Проверке»), обязательные фразы «второй этап воронки» и юнит-экономики в §9, называние ценового сегмента в вердикте и запрет безусловного «ВХОДИТЬ»; при нарушениях — 1 повторный вызов с feedback, после повторного провала отчёт принимается, а в UI выводится предупреждение `st.warning`. Карта спроса подставляется в секцию 7 из кода.
6. **Аккаунт, квота и история (Supabase)** — без входа доступен только экран
   «Вход / Регистрация»; перед каждым запуском LLM атомарно списывается один отчёт из
   квоты (`used/quota` в сайдбаре, окно 30 дней, дефолт квоты 0 до оплаты) — при
   падении LLM квота не возвращается (кредиты сожжены), а отчёт сохраняется со статусом
   `failed`. Успешный и упавший прогон попадают в «Мои отчёты»: метаданные, Markdown и
   исходный Excel (Storage); скачивание — Markdown, DOCX (pandoc) и Excel.

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # впишите ROUTERAI_API_KEY и ключи Supabase

streamlit run app.py
```

Откроется http://localhost:8501. Без аккаунта доступен только экран «Вход / Регистрация»;
после входа — разделы «Анализ» и «Мои отчёты». Загрузите `.xlsx`, укажите нишу и регион,
нажмите «Анализ».

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `ROUTERAI_API_KEY` | API-ключ (обязательна) | — |
| `ROUTERAI_BASE_URL` | Базовый URL API | `https://routerai.ru/api/v1` |
| `LLM_MODEL` | Модель | `openai/gpt-4o-mini` |
| `LLM_TIMEOUT` | Таймаут запроса, сек | `180` |
| `SUPABASE_URL` | URL проекта Supabase (обязательна) | — |
| `SUPABASE_ANON_KEY` | Anon-key (клиентская, для Auth) | — |
| `SUPABASE_SERVICE_ROLE_KEY` | Service-role key (**только сервер**) | — |

Ключи читаются только из env, в отчёт и логи не попадают; в UI service-role key не отображается.

## Настройка Supabase

1. Создайте проект на [supabase.com](https://supabase.com) (или в self-hosted).
2. В **SQL Editor** проекта выполните файл [`supabase/schema.sql`](supabase/schema.sql) —
   он создаёт таблицы `profiles`/`reports`, триггер профиля при регистрации,
   RPC списания квоты `consume_report_quota`, RLS-политики и приватный bucket `reports`.
3. В **Authentication → Providers** оставлен email+пароль; подтверждение email включено
   по умолчанию (письмо идёт через встроенный SMTP Supabase — при проблемах со спамом
   настройте свой SMTP в том же разделе).
4. Пропишите env-переменные `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY` (Settings → API) в `.env` локально и в Coolify.
5. **Выдача квоты**: дефолт квоты — 0 (доступ закрыт до оплаты). После оплаты откройте
   **Supabase Studio → Table Editor → profiles** и поставьте пользователю
   `quota_reports` (например, `5`); `used_reports` трогать не нужно — списание
   происходит автоматически при запуске анализа, окно 30 дней сбрасывается лениво.
6. Регистрация открыта; оплата — вручную (счёт/перевод), платёжного шлюза нет.

Файлы Excel хранятся в Storage по пути `reports/{user_id}/{report_id}.xlsx`
(приватный bucket, чужие файлы RLS не читает).

Фикстура `tests/fixtures/sample.xlsx` — синтетическая выгрузка по колонкам реального файла.

## Деплой в Coolify

1. Запушьте репозиторий в Git (приватный remote; добавьте deploy key Coolify).
2. В Coolify: **New Resource → GitHub/GitLab** → выберите репозиторий → **Build Pack: Dockerfile**.
3. Порт: **8501**.
4. Env-переменные в UI Coolify:
   - `ROUTERAI_API_KEY`
   - `ROUTERAI_BASE_URL=https://routerai.ru/api/v1`
   - `LLM_MODEL=openai/gpt-4o-mini`
   - `SUPABASE_URL=https://xxx.supabase.co`
   - `SUPABASE_ANON_KEY=...`
   - `SUPABASE_SERVICE_ROLE_KEY=...`
5. Домен и HTTPS — средствами Coolify (Traefik). Проверьте healthcheck `/_stcore/health`.
6. После деплоя — те же шаги настройки Supabase, что и локально (схема в SQL Editor,
   выдача квот в Studio).

### ⚠️ Безопасность

- `SUPABASE_SERVICE_ROLE_KEY` — только env сервера: она обходит RLS и даёт полный
  доступ к БД/Storage; в UI, отчётах и логах она не отображается и не сериализуется.
- RLS включён как защита на случай, если запрос уйдёт с user-JWT вместо service-role:
  пользователь читает только свои `profiles`, `reports` и файлы `reports/{user_id}/…`.
- Квота списывается атомарно в БД (RPC `consume_report_quota`, `for update`) — два
  браузера одного аккаунта не потратят больше лимита.
- Дефолтная квота 0: без выданного лимита запуск анализа блокируется, кредиты
  RouterAI не жгутся; остальные рекомендации прежние — не индексируйте домен
  (`X-Robots-Tag`, robots.txt), не публикуйте ссылку, не используйте ключ с большими лимитами.
