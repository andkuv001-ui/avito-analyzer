# Avito SERP Analyzer

Инструмент исследования ниши Avito для **решения о входе** (вторичный сценарий — обзор рынка для действующего продавца): анализ поисковой выдачи из Excel-файла — кластеры спроса, свежесть, конкуренты, незакрытые сценарии. Вход — Excel-выгрузка парсера поисковой выдачи по ключевому запросу + ниша и регион; выход — Markdown-отчёт-обзор факторов входа (секции 1–9) с явным вердиктом. Метрики и бакеты считает код, аналитику пишет LLM (OpenAI-совместимый API).

**Stateless**: история не сохраняется, БД нет, каждый запуск — новый анализ.

## Как это работает

1. **Парсинг Excel** — fuzzy-маппинг ядерных колонок (`Заголовок`, `Цена`, `Дата публикации`, `Просмотров всего`, `Платные услуги`, продавец, `категория 1–6` и т.д.). Товарные колонки ниши (`Высота`, `Материал`…) игнорируются с предупреждением. Нет ядерной колонки — значения `[НЕТ ДАННЫХ]`, анализ не ломается.
2. **Метрики (код)** — две категории объявлений: **свежие** («Дата публикации» ≤7 дней + подтверждение связкой «Просмотров сегодня» ↔ «Просмотров всего») и **старые** (всё остальное, включая продлённые). Время парсинга фиксируется и попадает в отчёт: «Просмотров сегодня» — главный сигнал эффективности, привязанный к нему. «Просмотры/день» не считаются: «Дата публикации» в выгрузке Avito — дата продления, а «Всего просмотров» накапливается за всю жизнь объявления. **Ценовая сегментация**: цена — конфаундер просмотров, поэтому объявления с числовой ценой делятся на три сегмента — **дешёвые / средние / дорогие** (тертили: дешёвые ≤ p33 < средние ≤ p66 < дорогие; <9 с ценой — сегменты не считаются, «договорная» и цена без числа — вне сегментов), и все разрезы просмотров (свежие vs старые, promo-эффект) считаются **внутри сегментов**.
3. **Стадия A (LLM, JSON, temperature=0)** — каждому объявления: теги кластеров (товарный / характеристический / сценарный / проблемный / коммерческий), B2C/B2B, поисковые запросы, УТП, сценарий. Retry 1× при невалидном JSON; при фолбэке карта спроса заполняется `[НЕТ ДАННЫХ]`.
4. **Дайджест (код)** — в него входят **ключевые факты, посчитанные кодом** (объём, классы свежести, нулевые просмотры, концентрация топ-10, promo-эффект, свежие vs старые, цена vs спрос, продавцы, кластеры без свежих, B2B-доля, топ-5 запросов, цены по кластерам; пустая база → `[НЕТ ДАННЫХ]`), **таблицы с ценовым контролем** — «Сегменты цены: дешёвые / средние / дорогие» (границы тертилей, N, цена min–med–max, медиана «Просмотров сегодня», доля платных услуг), «Свежие vs старые внутри ценовых сегментов», «Цены по кластерам» и «Эффективность свежих vs старых (без учёта цены)» с примечанием, что сравнение по всей выдаче конфаундится ценой, поля Стадии A в каждой записи (запросы, УТП, сценарий, тип) и **карта спроса (код)** — точные счётчики «кластеры × бакеты» плюс ценовые столбцы (цена-медиана и счётчики сегментов по тегу; <9 с ценой → `[НЕТ ДАННЫХ]`), числа от LLM не зависят.
5. **Стадия B (LLM)** — финальный Markdown-отчёт секций 1–9, организованный факторами решения о входе: §8 — гипотезы (строго 5–10 в формате `**Гипотеза N: …** — Основание: …; Проверка: …; Критерий успеха: <измеримый порог с числом>`; порядок гипотез = приоритет, гипотеза 1 — главная ставка и она же пункт 6 §9), §9 — «Решение о входе»: первая строка `**Вердикт:** ВХОДИТЬ | НЕ ВХОДИТЬ | ВХОДИТЬ ПРИ УСЛОВИИ …` (либо маркер `[НЕДОСТАТОЧНО ДАННЫХ ДЛЯ РЕШЕНИЯ]`) с ценовым позиционированием — в какой сегмент цены входишь — + ровно 7 пунктов `1)`–`7)` (п.7 — «что делаем → основание (цифра) → эффект/как измеряем (критерий успеха с числом)»); каждое утверждение §8–9 обязано опираться на цифру из дайджеста или содержать маркер `[НЕТ ДАННЫХ]` (в «Критерии успеха» маркер запрещён). Ответ проходит **валидацию Grounding** (`src/llm.py::validate_grounding`): подстроки «Основание»/«Проверка»/«Критерий успеха», числовой порог в критерии, цифра-цитата из дайджеста; при нарушениях — 1 повторный вызов с feedback, после повторного провала отчёт принимается, а в UI выводится предупреждение `st.warning`. Карта спроса подставляется в секцию 7 из кода.

## Локальный запуск

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # впишите ROUTERAI_API_KEY

streamlit run app.py
```

Откроется http://localhost:8501. Загрузите `.xlsx`, укажите нишу и регион, нажмите «Анализ».

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `ROUTERAI_API_KEY` | API-ключ (обязательна) | — |
| `ROUTERAI_BASE_URL` | Базовый URL API | `https://routerai.ru/api/v1` |
| `LLM_MODEL` | Модель | `openai/gpt-4o-mini` |
| `LLM_TIMEOUT` | Таймаут запроса, сек | `180` |

Ключ читается только из env, в отчёт и логи не попадает.

## Тесты

```bash
python -m pytest tests/
```

Покрытие: парсер дат (в т.ч. переход года), маппинг колонок, бакеты свежести, ценовые сегменты (тертили, малая база <9, «договорная» вне сегментов), сборка отчёта с секциями 1–9 и картой спроса из кода (в т.ч. ценовые столбцы), ключевые факты дайджеста и таблицы сегментов, поля Стадии A в дайджесте, валидация Grounding секций 8–9 (нормализация чисел, маркеры `[НЕТ ДАННЫХ]`, поле «Критерий успеха» с числовым порогом, вердикт, retry и warning). Фикстура `tests/fixtures/sample.xlsx` — синтетическая выгрузка по колонкам реального файла.

## Docker

```bash
docker build -t avito-analyzer .
docker run -p 8501:8501 -e ROUTERAI_API_KEY=sk-... avito-analyzer
```

Приложение слушает `0.0.0.0:8501`, healthcheck — `/_stcore/health`.

## Деплой в Coolify

1. Запушьте репозиторий в Git (приватный remote; добавьте deploy key Coolify).
2. В Coolify: **New Resource → GitHub/GitLab** → выберите репозиторий → **Build Pack: Dockerfile**.
3. Порт: **8501**.
4. Env-переменные в UI Coolify:
   - `ROUTERAI_API_KEY`
   - `ROUTERAI_BASE_URL=https://routerai.ru/api/v1`
   - `LLM_MODEL=openai/gpt-4o-mini`
5. Домен и HTTPS — средствами Coolify (Traefik). Проверьте healthcheck `/_stcore/health`.

### ⚠️ Безопасность

Приложение **без авторизации**: открытый URL позволит любому запускать анализ и жечь кредиты RouterAI. Рекомендации:

- не индексируйте домен (`X-Robots-Tag`, robots.txt) и не публикуйте ссылку;
- закройте доступ basic-auth / SSO на уровне прокси Traefik или домена в Coolify;
- не используйте ключ с большими лимитами.
